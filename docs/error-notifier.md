# Error notifier ("Biggbee — Error Notifier")

## Why the old emails were noisy and uninformative (verified 2026-10-29, n8n 2.27.4)

* **No global error workflow exists** (no workflow sets `settings.errorWorkflow`). Only the outbound workflow's own Error Trigger has ever fired.
* All 24 "Critical error" emails came from one cause: the outbound workflow's IMAP trigger, *Hostinger Email Trigger - Watch Replies*, losing its connection (`read ECONNRESET`, `write EPIPE`, `socket ended by the other party`, `Imap connection closed unexpectedly`). n8n logged "Will try to reactivate" and "Activation … was successful!" after each. One email per drop, nothing was down for more than ~2 seconds at a time.
* A trigger drop reaches the error workflow as `{ trigger: { error, mode }, workflow }` with **no `execution` object**. The old template only read `$json.execution…`, so everything printed "Unknown node / Unavailable" and the real message was discarded.
* Drops are not tied to connection age (see `docs/imap-force-reconnect.md`), so they are random server/network resets.

## Design

Two workflows' worth of logic, one source of truth:

* **`src/lib/alerts/throttle-core.mjs`**: pure decision/rendering logic (fingerprint, incident state machine, escalation, flood cap, wrap-up, email text). Unit tested.
* **`src/lib/alerts/atomic.mjs` + `src/app/api/internal/alerts/route.ts`**: the CRM makes the decision *atomically*.
* **`n8n/error-notifier/error-notifier.workflow.json`** (generated by `scripts/build-error-notifier-workflow.mjs`): `Error Trigger → Prepare Request → CRM Decide → Resolve Decision → { Log Error, Send Email? → Send Alert Email }`, and `Sweeper Schedule (30 min) → Prepare Sweep Request → CRM Sweep → Resolve Sweep → Send Alert Email`.

### The concurrency weakness, and the fix

n8n loads a workflow's static data when an execution **starts** and saves it when it **ends**, last writer wins. Executions that overlap all decide from the same snapshot and all but one update is lost. Measured on a model of that behaviour (`src/lib/alerts/fallback-race.test.mjs`): **100 simultaneous identical errors send 100 emails**, and a burst of 40 distinct failures bypasses the 10/hour flood cap (40 emails). n8n offers no lock, and static data is not transactional.

Fix: the decision runs inside the CRM JSON store's `updateCollection`, a per-collection promise queue where read → decide → write is one synchronous step, so every decision sees every earlier one. Verified against the **real store** with real concurrency:

| Scenario | Result |
|---|---|
| 100 simultaneous identical errors (in-process and over real HTTP) | 1 incident email + 1 escalation; count exactly 100 (no lost updates) |
| Same, restarted halfway (new process, same data) | nothing re-announced; count 100 |
| 40 simultaneous *distinct* failures, cap 10 | exactly 10 emails; 30 rolled into one digest; all 40 tracked |
| 20 identical + 5 distinct at once | the 5 distinct each email; identical → start + escalation only |
| 12 identical at once | exactly one `incident_started` and one `repeating` |
| 3 sweeps at the same instant | the wrap-up is sent once |
| HTTP retry of the same event id | same decision replayed, counted once (a lost response can neither lose nor double an alert) |
| Notifier's own failure / failure inside an error run | logged, never emailed, never tracked |
| 200 rapid writes | state file always valid JSON, no leftover temp files |

Idempotency: every request carries `eventId = <notifier workflow id>:<execution id>`; the CRM remembers the last 50 decisions.

### Fail-open fallback (when the CRM is unreachable)

If the CRM call times out, errors, returns non-JSON, 401/413/500 or an incomplete answer, `Resolve Decision` runs the same logic locally on static data and the email states: *"decided locally in n8n because the CRM alert service was unreachable. Duplicate suppression is approximate."* If even that throws, the raw error is emailed unthrottled. Property-tested over 300 random overlap schedules: the fallback can send **extra** emails but never leaves a failure without one (every failure that the atomic run emails about is emailed, and the first alert of each failure is always sent).

### What each email says

Workflow name + id, failing node name + id, execution id and link (or "none: activation errors occur outside an execution"), the payload's own timestamp, the real error and HTTP code, operation and affected service (from node type / URL host; query strings stripped), warning/critical, first occurrence / transient so far / recurring, impact, retries, next action, and incident counts. Anything the payload cannot supply is printed as **unavailable**; for trigger drops the underlying cause (`ECONNRESET` …) is not in the payload and the email says so. It never says "recovered", only "inferred from silence".

### Deduplication rules (settings: `CONFIG` at the top of the notifier's Code nodes; sent to the CRM with every call)

| Rule | Behaviour |
|---|---|
| Fingerprint | workflow id + node + error name + normalised message |
| Incident | same fingerprint < 180 min apart |
| First event of an incident | always emailed |
| Repeats | counted, not emailed; always written to the Errors sheet |
| Flapping | 5 within 60 min → one escalation, CRITICAL |
| Continued failure | at most one summary per 360 min |
| Wrap-up | after 180 min quiet, for incidents that repeated |
| Distinct failures | always emailed (subject to the global cap) |
| Flood cap | 10 emails/h; overflow in one digest |

## Honest limits

1. **Atomicity is per CRM process.** `updateCollection` serializes within one Node process (the CRM is one container). It is not a cross-process lock. Running two CRM processes against one data directory, or moving the CRM to several replicas, needs a real database with a unique constraint (e.g. `INSERT … ON CONFLICT` on the fingerprint). That is the recommended design if this ever scales; it is not needed today.
2. **The CRM is now a dependency of the alert path.** If it is down, the local fallback runs; during that time simultaneous identical errors can each email (extra emails, never missing ones).
3. **Recovery cannot be confirmed.** n8n alerts once per drop; its silent reactivation retries (1 s doubling to 24 h) have no API signal. A persistent outage and a recovery both look like silence. The wrap-up bounds how long a suppressed drop can go unmentioned (3 h after the last one) but cannot prove health.
4. Volume: replaying the 24 real alerts gives 10 incident emails + 8 wrap-ups = 18 (from 24); 96 identical failures/day collapse to 5. The remaining noise is only removable by stopping the drops, which a reconnect interval is unlikely to do (`docs/imap-force-reconnect.md`).
5. Two overlapping *sweeps* from the fallback path are not atomic (fallback only).

## State of production (released and verified 2026-10-30)

* CRM deployed with `POST /api/internal/alerts`. Verified: unauthenticated and wrong-key POST -> 401; valid key with a malformed body -> 400 (authenticated, nothing stored). `scripts/verify-alerts-endpoint.mjs` passes 8/8 against an isolated container of the **exact deployed image** (it is local-only by design: it fires 100+ synthetic errors, which on the production store would later be wrapped up by emails). The production alert store was left empty.
* `OWwCk77riM1yUmgT` was re-imported over the same id (node-for-node identical to `n8n/error-notifier/error-notifier.workflow.json`), calls `https://crm.biggbees.com/api/internal/alerts` with the existing "CRM Internal API Key" credential (checked: HTTP 400 on a deliberately invalid action, not 401), retries twice with the same `eventId`, and is **active** (its only trigger is the 30-minute sweeper).
* It is the **Error Workflow of `55q30dkVXZGwb8TR`** (outbound). That workflow is otherwise unchanged: still active, 101 nodes JSON-identical, same connections, credentials and IMAP static data. Backups of both live definitions are on the VPS (`/root/outbound-before-20261030.json`, `/root/error-notifier-before-20261030.json`).
* The IMAP reconnect interval was not changed.

Rollback: clear the Error Workflow setting on the outbound workflow; deactivate the notifier. The CRM endpoint is inert without callers.
